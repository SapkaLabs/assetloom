# Research: CLI, Compatibility, Documentation, and Package Verification

## JSON generation shape

**Decision**: `assetloom --json generate` writes direct canonical `GenerationResultV1`, not `{ ok, result }` and not changed-file arrays. Non-generation commands retain existing envelopes.

**Rationale**: Machine callers should have one schema across Node, stdout, and files. A success envelope changes the root contract and makes result validation conditional.

**Alternatives considered**:

- Retaining the envelope was rejected because it is not the same public contract.
- Adding a second versioned command was rejected because it fragments the authoritative workflow.
- Emitting both legacy and new shapes was rejected because stdout must contain exactly one unambiguous JSON document.

## Supported configuration versions

**Decision**: Route CLI generation for schema versions 1 and 2 through the existing `generateVersioned` engine. Keep plan/report/verify/clean dispatch where their contracts remain distinct and safe.

**Rationale**: `generateVersioned` already composes native and catalog tasks, ownership, recovery, typed descriptors, and complete results. One engine keeps the generation contract consistent while retaining legacy generated bytes.

**Alternatives considered**:

- Converting the old `generate` return into a synthetic result was rejected because it duplicates result assembly and can omit authoritative ownership semantics.
- Removing schema version 1 was rejected because its safe generation behavior remains supported.

## Result-file boundary

**Decision**: Interpret `--result-file` as a relative path beneath `.assetloom/results`; reject empty/absolute/`..`/NUL values, guard link traversal, and use atomic write-if-changed with canonical stable JSON.

**Rationale**: The constitution allows writes only beneath configured output roots or dedicated state. A result description is state, not a consumer file or generated artifact.

**Alternatives considered**:

- Arbitrary project-relative paths were rejected because they can target consumer-owned files.
- Treating the result file as a published artifact was rejected because it would recursively appear in its own catalog.
- Non-atomic direct writes were rejected because partial JSON could be mistaken for a valid result.

## Report and log streams

**Decision**: In JSON generation, stdout is reserved for canonical result JSON. Optional report/result notices use stderr or remain silent; human mode keeps a combined summary.

**Rationale**: Automation can parse stdout without filtering while operators still receive explicitly requested side-output locations.

**Alternatives considered**:

- Adding report metadata to result version 1 was rejected because it would change the public schema.
- Logging to stdout was rejected because it corrupts the JSON document.

## Compatibility facade

**Decision**: Retain safe `generate`, `generateV2`, and existing plan/verify/report/clean exports for source compatibility, but mark `generateVersioned` plus `GenerationResultV1` as authoritative. Do not restore any removed mutation port.

**Rationale**: Changed-list results remain useful to existing callers and do not violate the boundary, but new integrations need the complete portable catalog.

**Alternatives considered**:

- Removing every legacy API was rejected as unnecessary breakage.
- Keeping mutation adapters as deprecated plugins was rejected by the constitution and ADR.

## Packed-consumer proof

**Decision**: Pack all five workspaces, install tarballs with dependency lifecycle scripts disabled, validate manifests and packed text, compile public TypeScript imports with the repository compiler against the clean fixture, and run the installed CLI on a text-copy configuration.

**Rationale**: This detects workspace-link leakage, missing declarations/exports, invalid dependency ranges, absent CLI files, output-contract drift, and forbidden packed leftovers.

**Alternatives considered**:

- Workspace-only tests were rejected because they bypass tarball content and installation behavior.
- Publishing to a registry was rejected because remote changes are prohibited and local tarballs provide the evidence.
