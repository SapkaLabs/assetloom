# Feature Specification: Web Content Hashing and Usage Descriptors

**Feature Branch**: `mvp`
**Created**: 2026-08-02
**Status**: Draft
**Input**: Add explicit compatible, filename, and query cache-busting policies driven by final output bytes; isolate byte-affecting render fingerprints; and return deterministic typed web usage descriptors without mutating consumer applications.

## User Scenarios & Testing

### User Story 1 - Choose an explicit web cache policy (Priority: P1)

As a web caller, I can choose stable names, hash-bearing filenames, or hash-bearing query paths and receive public paths that match that policy.

**Why this priority**: Browser cache invalidation is the primary user-facing capability, and incorrect identity can serve stale assets.

**Independent Test**: Generate the same web resource under each policy and compare the published filename, returned public path, full digest, and shortened token.

**Acceptance Scenarios**:

1. **Given** no cache policy, **when** a web resource is generated, **then** its configured filename and public path are preserved.
2. **Given** filename cache busting, **when** final bytes are generated, **then** the filename contains the configured token derived from those bytes.
3. **Given** query cache busting, **when** final bytes are generated, **then** the filename is preserved and the returned public path ends with `?v=<token>`.
4. **Given** any policy, **when** generation succeeds, **then** the result contains the full SHA-256 digest and the exact cache token used where applicable.

---

### User Story 2 - Reuse renders across publication-only changes (Priority: P1)

As a maintainer or caller, changing only an output location, public URL, or unrelated configuration does not cause image bytes to be rendered again.

**Why this priority**: Render caching must represent generated content rather than project layout, otherwise harmless deployment changes waste work and obscure determinism.

**Independent Test**: Repeat materialization after changing only destination, public URL, and unrelated configuration while recording renderer invocations and generated bytes.

**Acceptance Scenarios**:

1. **Given** identical source bytes and effective transformation settings, **when** only the destination changes, **then** the existing materialized bytes are reused.
2. **Given** identical source bytes and effective transformation settings, **when** unrelated resource or target configuration changes, **then** the existing materialized bytes are reused.
3. **Given** a byte-affecting source, recipe, encoder, or renderer-compatibility change, **when** materialization runs, **then** it does not reuse a fingerprint for different final bytes.

---

### User Story 3 - Integrate web outputs as caller-owned data (Priority: P2)

As a web application owner, I receive typed, versioned usage descriptors that resolve to the complete returned artifact catalog so I can update my own HTML or framework code.

**Why this priority**: Consumers need deterministic integration guidance without granting AssetLoom permission to inspect or edit their projects.

**Independent Test**: Serialize a generated web result, resolve every descriptor artifact ID, and use the descriptor payload to construct caller-owned markup while sentinel consumer files remain unchanged.

**Acceptance Scenarios**:

1. **Given** generated favicons, images, or a complete web manifest, **when** generation completes, **then** each usage descriptor is typed, versioned, JSON-safe, deterministic, and references returned artifact IDs.
2. **Given** a filename or query cache policy, **when** a caller reads a descriptor, **then** its public path matches the published artifact and selected policy.
3. **Given** consumer HTML and application configuration beside the output root, **when** generation runs, **then** those files remain byte-for-byte unchanged.

---

### User Story 4 - Replace obsolete hash-named outputs safely (Priority: P2)

As a project owner, a new content hash replaces an obsolete AssetLoom-owned hash-named output without deleting a similarly named file that AssetLoom does not own.

**Why this priority**: Cache busting creates changing paths, so safe ownership-aware cleanup is necessary to avoid accumulating outputs or deleting user data.

**Independent Test**: Change final bytes after an initial filename-hashed generation and verify that only the predecessor recorded in the ownership manifest is removed.

**Acceptance Scenarios**:

1. **Given** a manifest-owned predecessor, **when** final bytes change under filename policy, **then** the new hash-named output is returned and the predecessor is reported and removed.
2. **Given** an unowned similarly named file, **when** generation changes hashes, **then** that file remains unchanged.

### Edge Cases

- Hash token lengths below or above the documented safe bounds are rejected before publication.
- Query cache busting preserves any configured public-path base and appends exactly one deterministic version parameter.
- If final encoded bytes remain identical despite an input or recipe change, their public content identity remains identical.
- Two planned outputs that resolve to the same case-normalized hash-bearing destination fail during preflight.
- A publication failure after rendering does not report success or remove an unowned predecessor.

## Requirements

### Functional Requirements

- **FR-001**: Web generation MUST support explicit `none`, `filename`, and `query` cache-busting policies.
- **FR-002**: The default policy MUST be `none`, preserving configured filenames and public paths for compatibility.
- **FR-003**: `filename` MUST place a deterministic shortened token from the final encoded output bytes in the published filename.
- **FR-004**: `query` MUST preserve the published filename and append `v=<token>` to the returned public path.
- **FR-005**: Every published artifact MUST return the full SHA-256 digest of final published bytes, independent of cache policy.
- **FR-006**: Every published artifact MUST return an exact deterministic token; for `filename` and `query`, this token MUST equal the token used in its cache-busting location.
- **FR-007**: Hash token length MUST be configurable and validated within a documented safe inclusive range.
- **FR-008**: Browser cache identity MUST NOT be derived from destination paths or source bytes alone.
- **FR-009**: Image materialization fingerprints MUST include source bytes, the effective byte-affecting recipe and encoding settings, renderer compatibility, and relevant algorithm versions.
- **FR-010**: Image materialization fingerprints MUST exclude unrelated configuration, output destinations, public URLs, timestamps, and absolute machine-specific paths.
- **FR-011**: Changing only excluded publication or unrelated configuration MUST reuse already materialized image bytes.
- **FR-012**: Changing a byte-affecting input MUST not reuse a cached materialization whose final bytes differ.
- **FR-013**: Web usage descriptors MUST be typed, versioned, deterministic, JSON-serializable, and reference artifact IDs present in the returned catalog.
- **FR-014**: Descriptor public paths MUST reflect the selected cache policy and final published paths.
- **FR-015**: AssetLoom MUST NOT inspect or modify consumer HTML, framework source, application manifests, or project configuration to apply descriptors.
- **FR-016**: Under filename policy, an obsolete predecessor MUST be removed only when recorded as AssetLoom-owned and MUST be included in the result's removed catalog.
- **FR-017**: Publication MUST render and hash final bytes before resolving a hash-bearing filename, then complete ownership/collision preflight before any output publication.
- **FR-018**: Existing unowned destinations and similarly named files MUST never be overwritten or removed.
- **FR-019**: Invalid legacy cache-policy values MUST fail with a stable `LOOM_` migration or configuration diagnostic.

### Key Entities

- **Web Cache Policy**: The selected `none`, `filename`, or `query` behavior plus a safe token length.
- **Final Content Identity**: The full digest and shortened token derived from final published bytes.
- **Render Fingerprint**: Internal identity containing only inputs capable of changing materialized bytes.
- **Web Usage Descriptor**: Versioned caller-owned integration data that references one or more published artifacts.
- **Published Web Artifact**: A complete owned output with normalized portable path, public path, disposition, and final content identity.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Automated policy tests produce the configured stable, filename-hashed, and query-hashed paths in 100% of covered cases while returning the same full digest for identical final bytes.
- **SC-002**: Destination-only, public-URL-only, and unrelated-configuration-only changes cause zero additional renderer invocations in automated cache tests.
- **SC-003**: Every returned web usage descriptor resolves all artifact IDs against the current result catalog and survives stable JSON serialization without information loss.
- **SC-004**: Ownership tests remove 100% of obsolete manifest-owned hash predecessors and 0 unowned similarly named files.
- **SC-005**: Consumer sentinel tests observe zero byte changes to HTML and application configuration during all three cache policies.
- **SC-006**: Repeated generation with identical inputs produces identical bytes, hashes, tokens, descriptor ordering, and result serialization, with zero content writes on the second run.

## Assumptions

- The documented safe token-length range is 8 through 64 hexadecimal characters, with 12 as the compatibility default when hashing is selected.
- `filename` is the recommended policy for immutable browser caching; `none` remains the compatibility default.
- Query policy uses the parameter name `v`; callers needing a different URL convention can transform descriptor data outside AssetLoom.
- Existing ownership manifests and bounded publication provide the authoritative cleanup and collision boundary.
- This feature changes no consumer project files and introduces no new resource type.
