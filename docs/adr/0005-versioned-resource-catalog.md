# ADR 0005: Versioned named-target resource catalog

Status: accepted.

## Context

Assetloom schema version 1 intentionally supports only the fixed `android` and
`ios` targets and the native app-icon, notification-icon, and splash-screen
resources. Applications also need deterministic shared files, generated SVG
components, image variants, web branding, and fonts. Encoding application names
or workspace paths in Assetloom would make that behavior difficult to reuse and
would put product policy in the generation engine.

## Decision

Schema version 1 remains a closed, native-only contract. Schema version 2 adds
named targets and a typed resource catalog. The `android` and `ios` target keys
are reserved and retain their version 1 shapes, so native resource definitions
do not acquire target IDs or application-specific paths. Other target keys are
configuration-defined IDs whose values use a `kind` discriminator.

Version 2 initially defines these target kinds:

- `directory`
- `react-native-library`
- `react-native-app`
- `web-app`

It defines these catalog resource types:

- `files`
- `svg-components`
- `image-variants`
- `native-image-assets`
- `web-app-branding`
- `font-family`

Catalog handlers validate a typed definition and produce declarative planned
artifacts. They do not write files. Source resolution, transformation, project
integration, publication, verification, and storage are application ports with
infrastructure adapters. A single typed registry dispatches resource types.

Planned catalog artifacts are executable discriminated recipes. Each recipe
contains the materialization inputs required by its operation and declares
either generated-file ownership or project-integration ownership. Target scope
is selected independently of artifact count so removing the last output for a
target can still drive manifest-safe stale cleanup.

`web-app-branding` is a semantic composite. Its handler expands branding into
typed image-variant, text, and project-integration artifacts; callers do not
need to declare an artificial companion `image-variants` resource. The contract
includes the display and short names, brand and icon-background colors,
foreground-scale policies, favicon/ICO/Apple-touch/application/maskable sizes,
content-hash naming and stable fallbacks, web-manifest metadata, SEO/site URL,
and optional static-web-app integration path needed to reproduce an inspected
web application. Assetloom core exposes only generic, versioned transformation
presets. Product-specific directory conventions are expressed through typed
configuration, such as an SVG component parent-directory prefix and separator,
or supplied by an application-owned adapter rather than embedded in core.

The existing native planner is retained behind a compatibility adapter. A
composite planner combines its unchanged tasks with catalog artifacts, applies
one destination collision check, and preserves deterministic destination
ordering. Version 1 callers continue to use the existing native loading and
planning APIs. Version-aware callers use the versioned loader and composite
planner.

React Native native icons, notification icons, and splash screens continue to
use the native planner. The catalog's `native-image-assets` resource expands a
source collection into configured Android density resources and complete iOS
image sets while preserving each source image's aspect ratio. Native font
registration is not migrated by this decision.

## Compatibility

ADR 0001 remains authoritative for schema version 1. This ADR supersedes its
native-only limitation only for schema version 2.

For a version 1 configuration, native task objects, IDs, source dependencies,
destinations, sort order, preset versions, renderer behavior, cache keys,
manifest entries, and generated bytes must remain unchanged. The version 1
schema continues to reject non-native target and resource properties.

The legacy `loadConfiguration` API remains version 1-only until catalog task
execution is available. `loadVersionedConfiguration` is the explicit boundary
for schema version 2, preventing partially implemented catalog configurations
from reaching the native executor.

## Ownership and safety

Target IDs and resource IDs use stable identifier syntax. Configured sources
and destinations remain subject to canonical declared-root containment,
symbolic-link checks, deterministic enumeration, and case-insensitive
destination collision detection.

Generated files may be manifest-owned. User-authored project files are never
generated-file-owned. HTML head metadata, web manifests, and static web app
configuration use typed, idempotent integration adapters with separately
persisted receipts. Those receipts describe only the managed state and support
compare-and-swap verification, safe updates, and target-scoped removal without
claiming ownership of the surrounding authored file. Additional project-file
integrations, including native-project integration, require the same typed
receipt contract. Arbitrary shell commands and executable configuration are
outside the catalog contract.

Generation is published as a resumable ordered transaction. Before the first
project mutation, Assetloom persists a guarded fingerprint of the desired final
manifest, owned outputs, authored integrations, receipts, configuration, and
target scope. Publication then advances through owned outputs and manifest,
catalog-authored files and receipts, native-authored files, and `.gitignore`.
The pending intent is cleared only after every phase succeeds. An identical
retry resumes idempotently from the durable state already published; a changed
configuration, source result, or target scope fails closed until the original
generation converges. Other commands do not operate while an intent is pending.

## Consequences

New resource types require a domain definition, schema definition, handler,
infrastructure adapters, and focused tests. They do not require application-name
conditionals in Assetloom. Version 2 execution and storage integration can be
implemented incrementally without altering the version 1 native pipeline.
