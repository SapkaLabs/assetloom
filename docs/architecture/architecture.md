# Assetloom architecture

## Workspace dependency graph

```text
@sapkalabs/assetloom-core
          ↑
@sapkalabs/assetloom-images
       ↗       ↖
@sapkalabs/assetloom-native   @sapkalabs/assetloom-web
       ↖       ↗
    @sapkalabs/assetloom (facade + CLI)
```

Core is resource-neutral. Images contains Sharp-backed implementation. Native
and web contain focused presets, validation, and typed usage contracts. Only
the facade contains Commander command definitions and the executable.

## Contract

Version 1 has two target values:

```ts
type TargetPlatform = 'android' | 'ios';
```

The architecture adds future native targets by adding a planner and target
content module. There is no generic framework-integration layer.

## Data flow

```text
ordered JSON files
        |
        v
parse -> merge -> schema + semantic validation -> path/source validation
        |                         |
        |                         +---- JSON-pointer provenance
        v
deterministic task plan -> collision check
        |
        v
render / compose / copy / complete bundle metadata
        |
        v
content cache -> conflict check -> bounded atomic write -> ownership manifest
        |
        v
structural verification of Assetloom-owned outputs
```

Web publication renders complete bytes before choosing browser identity. The
publisher hashes those final bytes, resolves a `none`, filename-token, or
query-token public path, preflights the resolved destinations and ownership,
then publishes. Changed hash-bearing predecessors are stale only when the prior
ownership manifest recorded them; filename patterns never authorize deletion.

Internal render identity is separate. Image cache aliases contain ordered
input-byte hashes, a path-free effective recipe, encoding settings, and
renderer/preset compatibility versions. Output roots, destinations, public
URLs, unrelated normalized configuration, timestamps, and absolute source
paths do not participate.

## Modules

- `config` parses ordered files, performs recursive object merge, array
  replacement and null deletion, validates the merged document, and records
  last-writer provenance for every JSON pointer.
- `domain` contains the public native target, task, resource, and stable error
  types.
- `planner` converts a validated configuration into destination-unique tasks.
- `resources` owns resource-level presets for app icons, notification icons,
  and splash screens.
- `renderers` converts safe SVG, PNG, and WebP sources into deterministic PNG
  or lossless WebP buffers.
- `targets` serializes complete platform resource-bundle metadata.
- `storage` owns content hashing, the render cache, project lock, atomic
  publication, safe cleanup, manifest, and recovery state.
- `verification` checks generated bytes without inspecting consumer projects.
- `api` and `cli` expose the same planning, generation, cleanup, and
  verification operations.

## Invariants

1. No write destination may resolve outside `project.root`.
2. Existing, unowned files are never overwritten, even when their bytes equal
   the planned output.
3. Cleanup removes only manifest-owned files whose current hash still equals
   the generated hash.
4. Tasks have stable IDs and preset versions; destination collisions fail
   before rendering.
5. Render-cache content is addressed by SHA-256 and verified when read.
6. Callers receive typed usage descriptors for application setup.
7. The manifest and recovery state are written only beneath `.assetloom`.
8. Public failures use stable `LOOM_` codes; dependency errors are retained as
   `cause`, never surfaced as the primary code.
9. Browser cache identity is the SHA-256 of final encoded bytes. Web policies
   are `none` (default), `filename` (recommended for immutable caching), and
   `query`; tokens are deterministic 8–64 character digest prefixes.
