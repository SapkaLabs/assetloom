# Assetloom architecture

## Contract

Version 1 has two target values:

```ts
type TargetPlatform = 'android' | 'ios';
```

The architecture adds future native targets by adding a planner and target
content module. There is no generic framework-integration layer.

## Data flow

```text
ordered JSON files
        |
        v
parse -> merge -> schema + semantic validation -> path/source validation
        |                         |
        |                         +---- JSON-pointer provenance
        v
deterministic task plan -> collision check
        |
        v
render / compose / copy / project update
        |
        v
content cache -> conflict check -> atomic write -> ownership manifest
                                              |
                                              +-> local Git ignore block
        |
        v
structural verification -> optional Gradle or Xcode build
```

## Modules

- `config` parses ordered files, performs recursive object merge, array
  replacement and null deletion, validates the merged document, and records
  last-writer provenance for every JSON pointer.
- `domain` contains the public native target, task, resource, and stable error
  types.
- `planner` converts a validated configuration into destination-unique tasks.
- `resources` owns resource-level presets for app icons, notification icons,
  and splash screens.
- `renderers` converts safe SVG, PNG, and WebP sources into deterministic PNG
  or lossless WebP buffers.
- `targets` serializes platform metadata and applies idempotent native-project
  integrations.
- `storage` owns content hashing, the render cache, project lock, atomic
  publication, safe cleanup, manifest, and local Git ignore block.
- `verification` checks generated bytes and can invoke native compilers.
- `api` and `cli` expose the same planning, generation, cleanup, and
  verification operations.

## Invariants

1. No write destination may resolve outside `project.root`.
2. Existing, unowned files are never overwritten unless their bytes already
   equal the planned output.
3. Cleanup removes only manifest-owned files whose current hash still equals
   the generated hash.
4. Tasks have stable IDs and preset versions; destination collisions fail
   before rendering.
5. Render-cache content is addressed by SHA-256 and verified when read.
6. Project integrations are idempotent and never become cleanup-owned files.
7. The manifest and local ignore block are written only when bytes change.
8. Public failures use stable `LOOM_` codes; dependency errors are retained as
   `cause`, never surfaced as the primary code.
